# v0.7.0 complete UART feature set and hardware validation

Date: 2026-11-05. Target: existing DX-LR32-A, CX32L003F8, SX1262/passive 32 MHz
crystal. The firmware implements all six requested extensions: instantaneous
RSSI, hardware statistics, RX gain, CAD, radio sleep/duty RX, and GFSK. Existing
LoRa configuration, raw packets, 433/868 MHz tuning, UART framing and recovery
remain available. Full formats are in [UART_FEATURES.md](UART_FEATURES.md).

ASan/UBSan, and real C config/parser/HAL cross-language tests. New coverage
includes GFSK staging/readback/invalid bitrate/shape rejection and LoRa recovery,

## Programming and boot

The known-target guard matched the recorded MCU and default USERCFG words.
Pre-program Flash matched the saved v0.6.0 recovery image. The same verified
CX32L003 programming procedure was used; no unlock, mass erase or option-byte
changes were needed. Full readbacks matched the programmed images.

An initial v0.7.0 build passed feature/peer tests. Final review then corrected
CAD cancellation to report DISABLED without a false RADIO_ERROR. This was an
intentional second program operation, followed by full feature/UART regression,
a physical long-CAD cancellation check and another full power cycle of the
exact final image. It was not a blind retry after a programming failure.

Local commands/configurations:

```sh
tools/openocd-cx32/bin/openocd \
  -s tools/openocd-cx32/share/openocd/scripts \
  -f logs/v0.7.0/preflight.cfg
tools/openocd-cx32/bin/openocd \
  -s tools/openocd-cx32/share/openocd/scripts \
  -f logs/v0.7.0/final-program.cfg
```

The final config sources the private identity guard, executes
`flash write_image erase firmware/build/meshctrl/controller.bin 0 bin`, then
`dump_image logs/v0.7.0/final-readback.bin 0 20212`. Comparisons run on the host;
no live SRAM-clobbering target checksum helper is used. v0.6.0 recovery remains
under `logs/v0.7.0/recovery-v060/`.

The user fully removed/restored module power. UART capture of the final image
received BOOT `00 07 00 00`, GET_VERSION `00 00 07 00 01` and PONG. Radio state
was idle RC 0x22, errors zero, active config invalid as expected after boot,
software counters zero and no RF attempt. ST-Link issued no start/reset command
during this final power-cycle capture. Normal operation does not require SWD.

A renewed CH340 attachment initially lacked Linux device permission; testing
continued after the user granted access to /dev/ttyUSB0. That was a host access
issue, not a firmware/USB-radio failure.

## RF packet tests

A suitable antenna was confirmed attached. All transmissions in this stage
used 433875000 Hz and -9 dBm commanded. No 868 MHz or maximum-power transmission
was performed.

One short raw GFSK packet, hex 44584C523037, was sent with explicit arming:

```sh
python3 bin/radio_features.py tx --modem gfsk --frequency 433875000 \
  --power -9 --hex 44584c523037 --transmit --log logs/v0.7.0/gfsk-tx.json
```

TX_DONE reported success after 7 ms. No GFSK peer was available: packet receipt,
GFSK interoperability and RF output were not established by TX_DONE.

The WSL public-channel EU_433 LongFast bridge then performed a real Alr1 test:

- Received `Alr1 v070 ready`, RSSI -25 dBm / SNR 7.25 dB.
- Sent one reply requesting `V070 OK`; TX_DONE succeeded and the user confirmed
  receipt in the phone app.
- Received `V070 OK`, RSSI -26 dBm / SNR 6.5 dB.

A separate 300 ms RX / 100 ms sleep duty session, without SPI polling, received
`Alr1 duty070` through DIO1-driven extraction/rearm: RSSI -27 dBm / SNR 6 dB.
STOP returned to RC. These peer checks preceded the final cancellation-only
reporting fix; the final image's feature/UART suites and CAD cancellation were
then rerun. Packet-path code did not change in that final correction.

The phone reported some outgoing broadcasts as failed despite receipt here.
The test bridge does not rebroadcast/ACK original packets; its independent text
reply is not an acknowledgement of the original packet ID. Ly01 being present
on an earlier day could explain earlier implicit acknowledgements, but that is
not proven by the logs. See [ESP32 delivery behavior](ESP32_INTEGRATION.md).

## ESP32 readiness and remaining qualification

All requested MCU commands are implemented, flashed and locally exercised.
The final power-cycle check leaves the MCU idle, awaiting UART configuration.
SWD wires can be removed for normal operation; future firmware upgrades still
require SWD. Shield replacement does not require a software setting.

The updated CYD Meshtastic overlay was also built successfully, with controller
0.7.0 handshake compatibility. It was **not uploaded or wired to the controller**
in this stage. App image: 1,317,552 B, SHA-256
`42a9dc11131b0a9f07230e8e8b2bf39380c855d4e00910de2ac6981c80a082b9`.
Use the [ESP32 integration guide](ESP32_INTEGRATION.md) before changing hosts.

Remaining tests include an actual GFSK peer, 868 MHz packet/performance tests,
RF output/current/thermal characterization, sustained/burst reception, and
full Meshtastic ACK/routing/PKI behavior through the wired ESP32 adapter. The
adapter retains conservative one-packet/cooldown constraints. Availability of
MCU CAD/sleep/GFSK commands does not automatically integrate those features into
Meshtastic. There is no arbitrary register interface, DIO2/DIO3 control, UART
bootloader or persistent user configuration in this image.

Evidence stays local under `logs/v0.7.0/`: readbacks, original/final boot and
power-cycle logs, feature/legacy regressions, GFSK TX, discovery/roundtrip,
duty-peer, cancellation, stack, static analysis and CYD build logs. Generated
binaries, dumps, identifiers, node keys and private session logs are excluded
from the source repository.

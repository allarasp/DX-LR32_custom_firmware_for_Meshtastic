# v0.6.0: direct UART frequency selection at 433 and 868 MHz

Date: 2026-11-04. One firmware image and the existing SET_FREQUENCY command
select either band. There is no separate band mode, enable token or special
label for 868 MHz. RX and TX use the applied frequency exactly as for 433 MHz.

## Usage

Run from the repository root, with the radio idle:

```sh
python3 bin/uart_radio.py bands
python3 bin/uart_radio.py configure --frequency 868000000 --power -9
python3 bin/uart_radio.py status
python3 bin/uart_radio.py configure --frequency 433875000 --power -9
```

These configure commands stage settings and APPLY them without transmitting.
The default modem parameters are SF11/BW250000/CR4/5, explicit header, CRC on,
normal IQ and sync 0x24B4; specify the existing CLI options to change them.
The host can instead send command 4 with a u32 Hz value followed by APPLY (8).
No extra command is required to select 433 or 868 MHz. Existing START_RX (9),
ARM_TX (21) and SEND_PACKET (11) operate in either configured band.

Accepted controller ranges are 433000000–434000000 Hz and
863000000–870000000 Hz; APPLY checks that configured bandwidth edges fit inside
the chosen range. The gap between ranges, 915 MHz and values outside the two
windows remain rejected. Commanded power stays -9..+22 dBm; regional power and
channel policy belong to the host. Existing TX arm/airtime/cooldown rules remain.

## Protocol and calibration

- Firmware version is 0.6.0, wire protocol remains 1.
- Capability bit 15 advertises GET_FREQUENCY_RANGES (24); mask is 0xFBFF.
- Command 24 has an empty request and a 19-byte reply: status:u8, schema:u8=1,
  count:u8=2, then minimum_hz:u32/maximum_hz:u32 for each range, little endian.
- The original 76-byte capabilities response is preserved. Its original module
  fields still describe the 433–532 MHz manufacturer declaration and its primary
  window fields still describe 433–434 MHz. Multi-band hosts query command 24
  for all accepted controller ranges; no field claims measured RF performance.
- RX/TX preparation selects CalibrateImage `98 6B 6F` for 433 MHz or
  `98 D7 DB` for 868 MHz automatically from the applied frequency. The HAL
  permits only those two calibration pairs and the two tuning windows.
- DIO2 RF-switch and DIO3 TCXO commands remain disabled. PC3/PC4 switching,
  UART recovery, version reporting and raw packet formats are retained.

Calibration source: [Semtech SX1261/2 datasheet Rev. 1.2, table 9-2](https://files.waveshare.com/wiki/SX1262-XXXM-LoRaWAN-GNSS-HAT/DS_SX1261-2_V1.2.pdf).
Controller tunability, successful status and RF link performance are separate
observations. No new matching/filter response, RF output, range or sensitivity
measurement was made in this stage.

## Programming and physical tests

The previous v0.5.1 image is saved in `logs/v0.6.0/recovery-v051/`. The known
CX32L003 identity guard passed; pre-program Flash matched that recovery image.
One guarded page-erase/program attempt succeeded at 100 kHz SWD. All 12,920 bytes
matched direct Flash readback; a later read after tests matched again. No unlock,
mass erase or option-byte change was required. Reset halted at the expected
handler/MSP, then UART BOOT was `00 06 00 00` and GET_VERSION `00 00 06 00 01`.

```sh
tools/openocd-cx32/bin/openocd \
  -s tools/openocd-cx32/share/openocd/scripts \
  -f logs/v0.6.0/preflight.cfg
tools/openocd-cx32/bin/openocd \
  -s tools/openocd-cx32/share/openocd/scripts \
  -f logs/v0.6.0/program.cfg
.venv/bin/python bin/test_live_controller.py \
  --log logs/v0.6.0/regression.json
```

The private programming config sources the identity guard before
`flash write_image erase firmware/build/meshctrl/controller.bin 0 bin`, then
`dump_image logs/v0.6.0/flash-readback.bin 0 12920`; comparisons are on the host.
No live target checksum helper was used. The reset procedure captured boot over
the CH340 while ST-Link reset/resumed the MCU. Raw/private configs and dumps
remain local.

Physical results:

1. GET_FREQUENCY_RANGES returned both exact windows through UART.
2. Ordinary SET_FREQUENCY/APPLY selected 868000000 Hz; config snapshot and
   available packet/sync/IQ readbacks passed. RX reported logical mode 3,
   chip status 0x52, device errors 0. Its 100 ms timeout produced RX_TIMEOUT,
   released the switch GPIOs and returned status to standby RC 0x22.
3. The same commands selected 433875000 Hz. The 100 ms RX/status/timeout/cleanup
   sequence passed again, with zero device errors.
4. Physical configuration at +22 dBm, power-limit rejection, alternate modem
   readbacks, CRC/truncated-frame recovery, 32 consecutive PINGs and the XOSC
   diagnostic all passed. Output-drop and UART-stall counters stayed zero.
5. The exact CLI configure examples above were also run for 868 and 433 MHz.

No RF transmission was performed on either band during this stage. Thus 868
MHz configuration, calibration and RX-state operation are physically checked,
but a real 868 MHz packet exchange and RF measurements remain to be done.
Previously verified 433 MHz peer exchanges are recorded in the v0.5.x results;
they are not presented as new v0.6.0 packet tests.

Final state is standby RC, zero device errors, valid 433875000 Hz/-9 dBm
configuration, switch GPIOs released. Three diagnostic RX timeouts and zero TX
attempts were recorded during the regression. Local evidence and outputs:
`logs/v0.6.0/` (boot, programming, regression, CLI, final status/SWD, stack and
build logs/readbacks), and `firmware/build/meshctrl/controller.{elf,bin,hex,map}`.
Private hardware/node identifiers, raw dumps and local logs remain excluded
